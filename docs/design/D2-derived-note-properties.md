# D2 — Производные свойства заметки

**Status:** Draft

**Связанные документы:** `docs/QUERY_LANGUAGE.md` §8, `shared/query-vectors.json`
(векторы свойств), `backend/internal/notes/`, `backend/internal/sqlitestore/`.

---

## Context

Часть полей языка запросов (D1) нельзя получить из готовой колонки:
`title` (текст первого `#`-заголовка), `tag` (список тегов), `has_code`,
`has_image`, `has_link`, `has_task_list`, `has_incomplete_tasks`. Их нужно
вычислять из текста заметки.

Наивный вариант — считать их «на лету» при каждом запросе: это проход по
всему тексту каждой заметки на каждый запрос, то есть запрос становится
O(размер библиотеки). Для персонального хранилища на тысячи заметок это
приемлемо только на бумаге.

Другой вариант — хранить свойства как отдельные таблицы и считать их
**источником истины**. Этот путь ломает главное свойство Noto: файл `.md` на
диске — источник истины, база только зеркалит. Если свойства станут
источником истины, то правка файла руками на диске перестанет быть
видимой, пока не пересчитают таблицы.

Значит, свойства — это **кэш**. Но кэш требует дисциплины: он должен
пересчитываться вовремя и должен честно признавать, когда он протух.

Отдельная проблема — два режима хранения. В запечатанном режиме сервер вообще
не видит текст заметок: свойства обязаны считаться в браузере, иначе
`has_code` в этом режиме будет всегда ложным.

## Decision

1. **Свойства — кэш, а не источник истины.** Файл `.md` остаётся источником
   истины; свойства — производная величина, которую всегда можно
   пересчитать из текста.

2. **Пересчёт в двух точках, и только в двух:**
   * **при сохранении заметки** — после успешной атомарной записи файла, до
     ответа клиенту (значит, поиск по свойствам сразу после сохранения
     находит заметку);
   * **при перестроении индекса** (`Reindex`) — полный проход по всем
     заметкам, который восстанавливает свойства после правки файла руками.

3. **Ошибка пересчёта не теряется молча.** Если свойства посчитать не удалось
   (например, файл повреждён), запись получает флаг `stale`: запросы видят
   «свойства неактуальны», а не «свойства отсутствуют». Явная пустота и
   явная неактуальность — разные вещи, и интерфейс должен их различать.

4. **Правила вычисления — простые и покрытые golden-векторами** (теми же,
   что у D1):
   * `title` — текст **первого** `#`-заголовка; если заголовка нет — пусто;
   * `tag` — `#` + слово из букв, цифр, `_`, `-`, `/`; тег заканчивается на
     первом символе, который не может быть частью тега; теги приводятся к
     нижнему регистру, порядок появления сохраняется, дубликаты убираются;
   * `#` внутри ограждённого блока кода не является тегом;
   * список задач — строка, начинающаяся с `- [ ]` / `- [x]` (также `*` и
     `+`); незакрытая задача делает `has_incomplete_tasks` истинным;
   * изображение — `![...](...)`, ссылка — `[[...]]` или `[...](...)`.

5. **Свойства вычисляются в том же месте, где исполняется запрос.** То есть
   две реализации — Go (открытый режим) и TypeScript (запечатанный режим) —
   и обе обязаны давать одинаковый результат на одинаковом тексте; проверка
   — golden-векторы.

6. **Свойства не хранятся в отдельных таблицах.** Они лежат рядом с
   метаданными заметки (одна запись на заметку, JSON-колонка), чтобы
   обновление свойств было одной транзакцией с записью метаданных.

## Consequences

**Возможности:**

* поля `title`, `tag`, `has_*` доступны в языке запросов и работают одинаково
  в обоих режимах хранения;
* перестроение индекса — это честное «приведи базу в соответствие с диском»,
  а не отдельный механизм;
* ошибка пересчёта видна, а не прячется.

**Издержки и обязанности:**

* две реализации правил вычисления (Go и TypeScript) — дублирование, которое
  удерживается golden-векторами;
* пересчёт при сохранении добавляет работу в путь записи: текст заметки
  разбирается ещё раз (нужно следить, чтобы это не уронило замеры записи);
* появляется третье состояние свойств («протухло»), и интерфейс должен его
  показывать, а не прятать.

**Открытые вопросы (до реализации):**

* где физически живёт флаг `stale` — в метаданных заметки или в отдельном
  счётчике состояния;
* показывается ли `stale` в интерфейсе заметки, в ответе API или только в
  диагностике;
* какой интервал пересчёта, если файл изменили мимо приложения и перестроение
  индекса не запускали (предварительно: только при перестроении индекса и при
  сохранении, без фонового таймера).

## Alternatives considered

| Вариант | Почему отвергнут |
|---|---|
| Считать свойства при каждом запросе | O(размер библиотеки) на каждый запрос; для большой библиотеки неприемлемо. |
| Хранить свойства как отдельные таблицы и считать источником истины | Разрушает главное свойство Noto: правка `.md` руками перестаёт быть видна. Кроме того, появляется вторая схема SQLite, которую надо версионировать. |
| Кэш только в памяти процесса | Теряется при перезапуске, не делится между открытыми вкладками, не работает в запечатанном режиме (там процесс вообще не видит текста). |
| Кэш только в SQLite | Не работает в запечатанном режиме: свойства всё равно пришлось бы считать в браузере. Нужны обе реализации в любом случае — вопрос только в том, где лежит кэш открытого режима. |
| Не считать свойства вообще, ограничить язык полями пути и имени | Язык запросов становится почти бесполезным: «что у меня по тегу `work`» — самый частый вопрос, и он не получал бы ответа. |
| Ошибка пересчёта = «свойств нет» | Тихо теряется информация: пользователь видит «нет картинок», хотя картинки есть, а пересчёт упал. Флаг `stale` отделяет «нет» от «не знаем». |
