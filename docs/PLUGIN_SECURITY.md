# Noto — безопасность плагинов

Документ описывает, от чего плагинная платформа **защищает**, а от чего —
**нет**. Правила не должны создавать ложного чувства защищённости: плагины в
Noto — это доверенный код, исполняемый в контексте приложения.

Связанные документы: [PLUGIN_API.md](PLUGIN_API.md) (контракт),
[PLUGIN_DEVELOPMENT.md](PLUGIN_DEVELOPMENT.md) (разработка),
[SECURITY.md](SECURITY.md) (модель безопасности приложения целиком).

---

## 1. Модель доверия — честно

> **Встроенные плагины — доверенный код. Изоляции и песочницы нет.**

Что это значит на практике:

* код плагина выполняется в том же окне, в том же контексте и с теми же
  привилегиями, что и само приложение;
* плагин **не** ограничен `PluginContext`: это удобная типизированная
  поверхность, а не принудительная граница доступа. Плагин может обратиться к
  `window`, `document`, `localStorage`, `fetch`, `indexedDB` и ко всему, что
  доступно странице;
* «песочница iframe», отдельный origin, изолированный контекст, отдельный
  процесс — этого в Noto нет и в текущей фазе не планируется;
* включение плагина — это решение владельца приложения, а не установка
  стороннего кода из интернета: плагины компилируются вместе с приложением.

Это же прямо написано в интерфейсе: панель управления плагинами показывает
предупреждение «Встроенные плагины выполняются как доверенный код в
приложении. Изоляции/песочницы нет.»
(`frontend/src/components/PluginManagerPanel.tsx:40-42`).

Отсюда следует правило безопасности №1: **вредоносный плагин может сделать
что угодно с вашими заметками.** Защита от этого — не механизм платформы, а
факт того, что плагины входят в сборку и проверяются в том же репозитории.

## 2. Модель разрешений

### Девять прав

Полный список — `PLUGIN_PERMISSIONS` (`frontend/src/plugins/manifest.ts:16`):

`notes.read`, `notes.write`, `tree.read`, `search.read`, `query.read`,
`editor.read`, `editor.write`, `ui.contribute`, `settings.write`.

Смысл каждого права — в [PLUGIN_API.md §3](PLUGIN_API.md#3-права-permissions).

### Как работает enforcement

**Проверка при регистрации.** `validateManifest`
(`frontend/src/plugins/manifest.ts:48`) отклоняет:

* неизвестное имя права → `unknown permission: <name>`;
* повторяющееся право → `duplicate permission: <name>`;
* `permissions` не массив → `permissions must be an array`.

Плагин с невалидным манифестом регистрируется в состоянии `failed`, его код не
выполняется, ошибка показывается в панели плагинов.

**Проверка совместимости.** Несовместимый `minApiVersion` → состояние
`incompatible`, активация не выполняется.

**Проверка при каждой операции.** Механизм живёт в
`frontend/src/core/api/pluginApi.ts`:

* `PluginPermissionError` — класс ошибки. Он объявлен в `core`, потому что
  `core/**` не может импортировать `src/plugins/**` (правило R1), и
  **реэкспортируется из контракта**
  (`export { PluginPermissionError } from '../core/api/pluginApi'` в
  `frontend/src/plugins/contract.ts`), поэтому плагин может поймать его по типу.
  Сообщение содержит только идентификатор плагина и имя недостающего права —
  содержимого заметок в нём нет, поэтому ошибку безопасно логировать.
* `requirePermission(pluginId, permissions, permission)` — бросает
  `PluginPermissionError`, если права нет.
* `PLUGIN_API_PERMISSIONS` — таблица «операция → право»
  (`getNote → notes.read`, `saveNote → notes.write`, `getTree → tree.read`,
  `search → search.read`).
* `restrictPluginApi(api, pluginId, permissions)` — возвращает **новый**
  объект, который проверяет права перед каждым вызовом.
* `restrictEditor(editor, pluginId, permissions)` — то же для редактора.

Хост (`frontend/src/plugins/host.ts`) собирает контекст так, что плагин
получает **только ограниченные обёртки**:

| Операция | Требуемое право |
| --- | --- |
| `ctx.api.getNote(path)` | `notes.read` |
| `ctx.api.saveNote(path, content, revision)` | `notes.write` |
| `ctx.api.getTree()` | `tree.read` |
| `ctx.api.search(query, limit?)` | `search.read` |
| `ctx.editor.getText()` / `getSelection()` / `getCursor()` | `editor.read` |
| `ctx.editor.onChange()` / `onSelectionChange()` | `editor.read` |
| `ctx.editor.insert()` / `insertAt()` / `replaceSelection()` | `editor.write` |
| `ctx.editor.focus()` / `openSearch()` / `getPath()` | без права (не меняют и не читают содержимое) |
| `ctx.registerCommand()` и остальные `register*` | `ui.contribute` |
| `ctx.settings.set()` / `reset()` | `settings.write` |
| `ctx.settings.get()` / `all()` | без права (пространство принадлежит плагину) |
| `ctx.on(...)`, `ctx.onEditor(...)` | без права (только метаданные) |

Набор прав — замороженная копия `manifest.permissions`
(`Object.freeze([...manifest.permissions])`): плагин не может изменить его
изнутри, а `ctx.permissions` — read-only.

Отказ — это **исключение в коде плагина**, а не тихий no-op. Если
`PluginPermissionError` брошен во время `activate`, хост считает это не
поломкой плагина: плагин остаётся `active` со своими регистрациями, а причина
попадает в реестр («plugin activation stopped by a permission error»).

### Чего enforcement не покрывает

* **Содержимое, которое плагин уже прочитал.** Право `editor.read` даёт текст
  открытой заметки целиком (`ctx.editor.getText()`); `notes.read` — тело любой
  заметки, `tree.read` — дерево, `search.read` — фрагменты найденных заметок.
* **Сетевые запросы мимо API.** Платформа не даёт плагину HTTP-клиент, но и не
  запрещает ему вызвать `fetch` самому: CSP приложения
  (`connect-src 'self'`, см. `docs/CONTRACT.md` §5) разрешает запросы к
  собственному origin, а именно там живёт API. То есть плагин технически
  может обратиться к `/api/*` в обход фасада и обойти проверку прав.
* **Возможности самого языка.** Плагин — доверенный код: у него есть
  `window`, `document`, `localStorage`, `indexedDB` и `fetch`.
* **Фильтрацию содержимого в логах.** Правило «плагин не логирует текст
  заметки» существует только как правило (см. §5).
* **Чужие данные вне контекста.** Проверка прав не помогает, если плагин
  прочитал данные раньше и положил их в свои настройки.

## 3. Запреты

| Запрет | Как обеспечивается |
| --- | --- |
| Никаких `eval` / `new Function` | В коде платформы и встроенных плагинов их нет; встроенные плагины собираются бандлером, и `manifest.ts` явно фиксирует это как правило модели. Автоматического запрета на уровне рантайма нет — запрет обеспечивается ревью и границами импортов. |
| Никакой загрузки удалённого JS | Список плагинов статический: `builtinPlugins` (`frontend/src/plugins/loader.ts:18`) — литерал массива, собираемый бандлером. Динамического `import()` по URL/specifier'у из данных нет. |
| Никакого `import()` по произвольному пути | В `src/plugins/**` нет динамических импортов; единственный известный `import('idb')` — в `core/settings/settingsStore.ts` и он касается локальной библиотеки. |
| Никаких `import.meta.glob` в плагинах | Не используются; плагины перечисляются статическим массивом. |
| Плагин не может регистрироваться по идентификатору из пользовательского ввода | `builtinPlugins` — статический список; `PluginRegistry.register` отклоняет дубликат `id`, а id проверяется регулярным выражением `/^[a-z0-9][a-z0-9._-]*$/` (`frontend/src/plugins/manifest.ts:27`). Идентификатор плагина никогда не используется как путь, URL или спецификатор модуля. |
| Плагин не лезет в чужое пространство настроек | Ключ настройки — `<pluginId>:<settingKey>`, а `pluginId` знает только хост; наружу отдаются только методы с явным `pluginId`. |

Границы импортов проверяются автоматически:
`frontend/scripts/check-boundaries.mjs` (правила R1–R12), запуск —
`npm run check:boundaries`.

## 4. Целостность данных

### Запись только через ревизию

Плагин пишет заметку только через `ctx.api.saveNote(path, content, revision)`.
Фасад (`frontend/src/core/api/pluginApi.ts:56`) передаёт ревизию в
`src/api/notes.ts` без изменений, а сервер применяет optimistic locking:

* если переданная ревизия совпадает с сохранённой — запись выполняется,
  ревизия увеличивается;
* если ревизия устарела — сервер отвечает `409 revision_conflict` и
  возвращает актуальное состояние заметки в `error.current`.

Значит, плагин **не может** незаметно затереть чужую правку: либо он знает
актуальную ревизию, либо получает конфликт. Ошибка пробрасывается плагину
без изменений (`ApiError` с `code === 'revision_conflict'`), её можно
обработать.

Плагин не может и «угнать» запись: `revision === 0` (принудительная запись)
в фасаде не блокируется отдельно, но использовать его плагину не следует —
в `PluginApi` это тот же вызов, а ответственность лежит на коде плагина.
Фактической защиты от `revision === 0` на уровне фасада сейчас нет.

### Аудит: события после успешной операции

События для плагинов эмитятся **после** того, как операция завершилась
успешно:

* фронтенд: `note.created`, `note.updated`, `note.deleted`, `note.renamed`,
  `note.moved`, `folder.created`, `editor.saved`, `workspace.opened`
  (`frontend/src/App.tsx:215-262`) — эмитятся по результату действия
  пользователя, а не по оптимистичной модели;
* бэкенд: `Service.fireHooks` вызывается после того, как диск, поисковый
  индекс и метаданные пришли в согласованное состояние и после снятия
  блокировок (`backend/internal/notes/notes.go:99-108`,
  `backend/internal/notes/notes_move.go:136-145`,
  `backend/internal/notes/trash.go:67-76`, `backend/internal/notes/trash.go:224-234`).
  Хук выполняется синхронно, в порядке регистрации; паника восстанавливается
  и логируется, операция сохраняет свой результат.

Событие `note.updated` не эмитится, если заметка не открылась или статус
сохранения — `error` (`frontend/src/App.tsx:214`). Payload событий не содержит
содержимого заметок.

### Изоляция ошибок

* Ошибка в `activate` → состояние `failed`, все регистрации плагина снимаются,
  наружу ошибка не пробрасывается.
* Ошибка в подписчике события → логируется, остальные подписчики получают
  событие.
* Ошибка рендера вклада → `PluginErrorBoundary` показывает «Ошибка плагина:
  …» вместо падения страницы.
* Ошибка в колбэке `onDeactivate` → логируется, остальные колбэки выполняются.

## 5. Логирование и приватность данных

`PluginLogger` (`frontend/src/plugins/contract.ts:74`) — это
`createLogger(scope)` из `frontend/src/core/diagnostics/logger.ts`: каждая
строка получает префикс `[noto:<pluginId>]` и уходит в `console`.

Правило: **плагин не должен логировать содержимое заметок.** Это правило
соблюдается авторами плагинов, а не механизмом:

* логгер только добавляет префикс и **не инспектирует** переданные значения
  (это прямо написано в комментарии `frontend/src/core/diagnostics/logger.ts:7-10`);
* если плагин передаст текст заметки в `ctx.logger.debug(...)`, он попадёт в
  консоль браузера как есть — фильтрации нет;
* встроенный `word-count` в лог пишет только счётчики, а не текст
  (`frontend/src/plugins/builtin/word-count/index.ts:194-197`).

Серверная сторона ведёт себя строже: содержимое заметок не логируется вовсе
(`docs/CONTRACT.md` §6, `docs/SECURITY.md`).

## 6. Политика service worker после фазы 2

Service worker — `frontend/public/sw.js`.

| Маршрут | Политика | Что это значит |
| --- | --- | --- |
| `/api/*` (включая `/api/health`) | **network-only** | Ответ никогда не попадает в кэш. При отсутствии сети клиент получает `503` с конвертом `{ "error": { "code": "network_error", "message": "Noto is offline: the server could not be reached." } }` (`frontend/public/sw.js:104-124`). |
| Мутации (`POST`/`PUT`/`DELETE` и т. п.) | network-only + очистка кэша | Успешная мутация удаляет любые следы приватных API-ответов из кэшей (`clearPrivateApiCache`, `frontend/public/sw.js:127-146`). |
| Статические ассеты (`GET`) | cache-first | Кэшируются в `*-assets`. |
| Оболочка приложения (`/`, `/index.html`, манифест, иконки) | precache + navigation fallback | Приложение открывается офлайн. |

Приватность: приватные ответы (`/api/notes`, `/api/tree`, `/api/search`,
`/api/trash`, `/api/attachments`) **никогда** не кэшируются, поэтому офлайн
не может показать устаревшее тело заметки. Кэш приватного API удаляется и при
активации новой версии worker'а, и после каждой успешной мутации; старые
`-api`-кэши вычищаются.

Что это значит для плагинов: данные, полученные плагином через `ctx.api`,
не переживают офлайн-сессию через кэш service worker'а — вместо устаревших
данных придёт явная ошибка `network_error`. Черновики (IndexedDB) и настройки
плагинов (IndexedDB `noto-plugins`) живут отдельно.

Ограничение: это политика кэширования, а не защита от утечки через
консоль браузера или расширения.

## 7. Модель настроек

* Отдельная база IndexedDB **`noto-plugins`** (`frontend/src/core/settings/settingsStore.ts:18`),
  не та, что у черновиков; хранилища `settings` (значения) и `meta`
  (состояния плагинов и версии схем настроек).
* Пространство имён: составной ключ `<pluginId>:<settingKey>`. Все методы
  `SettingsStore` принимают `pluginId` явным параметром, и знает его только
  хост — плагин не может адресовать чужое пространство. Это проверяется тестом
  «does not leak the values of another plugin into getAll».
* **Битые значения → дефолт.** Значение, не переживающее JSON-цикл, отбрасывается:
  `get` возвращает значение по умолчанию из схемы манифеста и пишет
  `[noto:settings] corrupted value for <id>:<key>, using default`.
  Ограничение: если у ключа есть значение по умолчанию в схеме манифеста,
  неправильный тип также приводит к значению по умолчанию
  (`[noto:settings] value for <id>:<key> has type …, expected …, using
  default`); для ключей вне схемы тип не проверяется и значение возвращается
  как есть.
* **Миграции `settingsVersion`.** Плагин объявляет `settingsVersion` и карту
  `settingsMigrations`; хост применяет миграции по порядку при активации
  (`SettingsStore.migrateSettings`, `frontend/src/core/settings/settingsStore.ts:193`).
  Пропущенный шаг миграции останавливает цепочку; ошибка миграции одного
  значения не проваливает активацию.
* Настройки не содержат содержимого заметок по назначению, но платформа этого
  не проверяет — плагин может записать в настройки что угодно, что переживает
  JSON.

## 8. Ограничения и что не поддерживается

* **Пользовательские плагины устанавливаются из файла и по URL.** Манифест
  плагина проверяется при установке, целостность манифеста сверяется с
  указанным хешем, но **код установленного плагина не исполняется**: он
  показывается в списке и ждёт включения. Исполняемый код по-прежнему
  приезжает только вместе со сборкой приложения.
* **Песочница есть, но её объём ограничен.** Плагин, который объявляет
  `manifest.sandbox = true`, исполняется в iframe со строгим CSP
  (`default-src 'none'; script-src 'nonce-…'; connect-src 'none'`) и без
  `allow-same-origin`. Правило **R17** чекера границ запрещает в исходнике
  такого плагина `eval`, `new Function`, динамический `import(`, `fetch`,
  `XMLHttpRequest` и `WebSocket`.
* **Встроенные плагины без `manifest.sandbox` исполняются как доверенный код**
  в контексте приложения: изоляции, отдельных origin'ов и ограничений сети
  для них по-прежнему нет.
* **Права применяются только к API, редактору, UI-вкладу и записи настроек.**
  Сетевые вызовы мимо API (через `fetch`) проверками не покрыты.
* **Плагин может ходить в сеть сам** через `fetch` — платформа этого не
  запрещает, CSP разрешает `connect-src 'self'`. Для плагина в песочнице
  сеть закрыта правилом R17 и самим CSP.
* **Плагин не может читать чужое пространство настроек**, но может прочитать
  и записать **своё**, в том числе положить туда произвольные данные.
* **Логирование содержимого запрещено правилом, но технически не
  фильтруется** (см. §5).
* **Плагины не могут менять схему БД, обходить ревизии, трогать чужие
  настройки и грузить удалённый код** — это следствие контракта
  ([PLUGIN_API.md §12](PLUGIN_API.md#12-что-может-плагин-а-что--нет)).
* **Офлайн-очередь приложения плагинам недоступна**: она живёт в ядре
  (`core/sync/`) и плагины её не видят.
* **Журнал действий плагинов есть**: каждое чтение, запись, открытие и команда
  плагина попадают в кольцевой буфер из 500 записей (`src/plugins/audit.ts`),
  который показывает менеджер плагинов. Это журнал действий, а не содержимого
  заметок.

## 9. Граница ключевого материала

Хранилище заметок бывает зашифрованным: в этом режиме ключ выводится из
мастер-пароля в браузере и живёт только в памяти вкладки. Плагин не должен
дотянуться до этого ключа — и не может.

### 9.1. Что плагин видит, а что нет

| Плагин видит | Плагин не видит |
|---|---|
| `ctx.vault.mode` (`open` / `sealed`) | мастер-пароль |
| `ctx.vault.encrypted` | KEK (ключ шифрования ключа) |
| `ctx.vault.locked` | DEK (ключ данных) |
| `ctx.vault.formatVersion` | эпохи ключей, соль KDF, завёрнутые копии ключа |
| содержимое заметки через `ctx.api` (то же, что и в открытом режиме) | файлы `.noto/keystore.json`, `.noto/objects/**`, `.noto/manifests/**` |

`ctx.vault` — это **состояние**, а не доступ: четыре поля, замороженная копия
(`Object.freeze`), без ключевого материала. Плагин может спросить «хранилище
зашифровано?» и не может спросить «ключ».

### 9.2. Почему это нельзя обещать только словами

Материал ключей живёт в двух модулях: `src/core/crypto/keys` (иерархия ключей,
эпохи, key wrapping, ключ восстановления) и `src/core/crypto/sealed`
(контейнер, AES-256-GCM). Ограничение на импорты превращает «плагин не
получит ключ» из обещания в проверку:

| Правило | Что запрещает | Где |
| --- | --- | --- |
| **R11** | `src/plugins/**` не может импортировать `src/core/crypto/**` | `frontend/scripts/check-boundaries.mjs` |
| **R12** | `src/core/crypto/keys` и `src/core/crypto/sealed` импортируются **только** из `src/core/crypto/**` и `src/core/vault/**` | там же |

Дополнительно **R10** запрещает `src/core/crypto/**` импортировать
`src/core/vault/**`: зависимость направлена только в одну сторону, поэтому
крипто-ядро остаётся листом графа и его нельзя случайно «протянуть» к
хранилищу.

Нарушение — падение `npm run check:boundaries`, а не замечание на ревью.

### 9.3. Что видно через запрос (API 1.2.0)

Право `query.read` даёт плагину выборку заметок. Плагин видит:

* пути, имена, сниппеты и заголовки совпавших заметок;
* имена тегов и число заметок, которые их несут;
* в запечатанном режиме — те же данные, вычисленные **в браузере** над
  расшифрованными заметками (`frontend/src/core/api/pluginQuery.ts`).

Плагин не видит:

* мастер-пароль, KEK, DEK и любые производные от них величины;
* ключевой материал шифрования;
* заметки, которые не совпали с запросом — запрос не является обходом
  ограничения `notes.read`: тело заметки по-прежнему читается только через
  `ctx.api.getNote(path)` и только с правом `notes.read`.

Запрос — это фильтр, а не новый канал доступа к данным: те же права
(`query.read` и, отдельно, `notes.read` для чтения тела) проверяются в
`restrictPluginApi` перед каждым вызовом.

### 9.4. Чего эта граница не покрывает

Честно: песочница есть только у плагинов, которые объявляют
`manifest.sandbox = true` (см. §8), и правила импортов — это
**статическая** гарантия, а не изоляция времени выполнения. Встроенный
плагин без песочницы исполняется как доверенный код в том же окне. Поэтому граница ключей
держится на трёх уровнях сразу:

1. **Статически** — правила R11 и R12 не дают импортировать крипто-ядро.
2. **Структурно** — `ctx.vault` содержит четыре поля и не содержит ключа;
   публикует состояние приложение, а не плагин.
3. **Соглашением** — плагин не кэширует содержимое заметки вне ядра и не
   читает файлы `.noto` напрямую. Это правило проверяется ревью и тестами,
   а не компилятором: расшифрованный текст, попавший в `localStorage`
   плагина, скомпрометирует хранилище, даже если ключ остался в памяти
   вкладки.

Практические следствия для автора плагина — в
[PLUGIN_DEVELOPMENT.md §10](PLUGIN_DEVELOPMENT.md).
