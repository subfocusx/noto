# Noto — шифрование хранилища (режим `sealed`)

Документ описывает сквозное шифрование хранилища Noto: где живёт криптография,
какие примитивы выбраны и почему, что именно защищено, что **не** защищено, как
устроен формат на диске и как проверить безопасность.

Смежные документы: [`VAULT.md`](VAULT.md) (открытое хранилище и его раскладка),
[`SECURITY.md`](SECURITY.md) (модель безопасности сервера),
[`PLUGIN_SECURITY.md`](PLUGIN_SECURITY.md) (модель доверия плагинов),
[`CONTRACT.md`](CONTRACT.md) (авторитетный внутренний контракт).

> **Язык терминов.** «Открытое хранилище» — обычный режим, где заметки лежат
> `*.md`, а метаданные — в SQLite. «Запечатанное хранилище» (`sealed`) — режим,
> в котором на диск попадает только шифротекст. «Провайдер» — OneDrive,
> Google Drive, Dropbox или любая другая система, которая синхронизирует папку.

---

## 1. Зачем это нужно

Заметки Noto лежат в обычной папке, которую пользователь синхронизирует с
облачным диском. По умолчанию эта папка — открытая: `*.md`, `noto.db`,
`attachments/`. Облачный провайдер (и любой, кто получил копию папки) видит
заголовок заметки, её текст и вложения.

Запечатанный режим меняет одно правило: **шифрование происходит в браузере,
до записи на диск**. На диск, а значит и в облако, попадает только шифротекст.
Провайдер никогда не получает ключ и не может прочитать содержимое, даже если
он полностью контролирует сервер Noto.

Это свойство называется **zero knowledge**: сервер Noto — слепое хранилище
объектов, а не доверенный посредник. Криптографическая граница проходит по
краю браузера, а не по краю сервера.

### 1.1. Модель угроз

| Угроза | Защита | Ограничение |
|---|---|---|
| Облачный провайдер читает содержимое заметок | Ключ никогда не покидает браузер; на диске только шифротекст | Провайдер видит метаданные: имена файлов объектов, их размеры, время изменения, частоту синхронизации |
| Оператор сервера Noto или человек с доступом к диску сервера | Сервер — слепое хранилище: он не знает ключа и не разбирает контейнер | Сервер видит размеры и время; в режиме `sealed` он не создаёт базу SQLite вообще |
| Потерянный или украденный ноутбук без разблокировки диска | Файлы бесполезны без мастер-пароля | Если атакующий имеет права администратора на машине, он может дождаться разблокировки или прочитать память процесса |
| Офлайн-перебор украденного хранилища | Argon2id — функция, устойчивая к аппаратному ускорению (memory-hard) | Слабый мастер-пароль остаётся слабым; «лёгкий» пресет KDF ослабляет вывод ключа ещё сильнее |
| Подмена или порча данных синхронизацией | AES-256-GCM: изменённый шифротекст или заголовок ломает проверку подлинности | Проверка обнаруживает подмену, но не восстанавливает данные — нужен бэкап |
| Удалённая заметка «осталась» в облаке | — | **Копии в истории версий, в снимках и в бэкапах провайдера не стираются.** Удаление файла не удаляет их |

### 1.2. Что честно НЕ защищено

Этот список — часть контракта, а не оговорка.

* **Администратор машины и вредоносное ПО.** Пока хранилище разблокировано,
  ключевой материал лежит в памяти вкладки. Кто умеет читать память процесса
  браузера или перехватывать его API, получит доступ к открытому тексту.
* **Модифицированный клиент.** Целостность приложения не проверяется: если
  злоумышленник подменит фронтенд, он сможет exfiltrate ключ при разблокировке.
  Защита от этого — проверка кода сборки, а не криптография.
* **Транспорт до локального бэкенда.** Запросы идут по обычному HTTP на
  `127.0.0.1` (loopback). Данные уже зашифрованы, но сам канал не имеет
  TLS-защиты; это не мешает, потому что полезная нагрузка — шифротекст.
* **Восстановление ключей.** Без мастер-пароля и без ключа восстановления
  хранилище открыть нельзя. Ни у разработчика, ни в приложении, ни в облаке
  нет «запасного» ключа — это осознанное решение, а не недоработка.
* **История на стороне провайдера.** Удаление plaintext-файла (или запечатанного
  объекта) не удаляет копии из истории версий OneDrive/Google Drive/Dropbox, из
  снимков и из резервных копий провайдера.

## 2. Где живёт криптография

### 2.1. В браузере, а не на сервере

```
   ┌───────────────────────────────────────────────┐
   │  Браузер (единственное место, где есть ключ)  │
   │                                               │
   │  src/core/crypto/**   ← KDF, AES-GCM, keystore │
   │  src/core/vault/**    ← чтение/запись, манифест│
   │         │                                     │
   │         │  уже зашифровано                   │
   │         ▼                                     │
   │  HTTP-запрос с шифротекстом                   │
   └───────────────┬───────────────────────────────┘
                   ▼
   ┌───────────────────────────────────────────────┐
   │  Бэкенд: слепое хранилище объектов            │
   │  backend/internal/sealed/**                   │
   │  Не знает ключа. Не разбирает контейнер.       │
   └───────────────┬───────────────────────────────┘
                   ▼
        OneDrive / Google Drive / Dropbox
        (получают только шифротекст)
```

Бэкенд — это «тупой» объектный сторадж: он принимает байты под
идентификатором, проверяет форму идентификатора, пишет атомарно и отдаёт байты
обратно. Он не знает, что такое заметка, заголовок или путь.

### 2.2. Изоляция крипто-ядра

| Модуль | Ответственность |
|---|---|
| `frontend/src/core/crypto/kdf.ts` | Argon2id, параметры вывода ключа, соль |
| `frontend/src/core/crypto/sealed.ts` | AES-256-GCM через `crypto.subtle`, контейнер, чанки |
| `frontend/src/core/crypto/keys.ts` | Иерархия ключей, keystore, эпохи, ключ восстановления |
| `frontend/src/core/crypto/format.ts` | Заголовок контейнера, base64/hex |
| `frontend/src/core/crypto/errors.ts` | Типизированные ошибки (`CryptoError`, `KeyUnlockError`, `AuthenticationError`, `SealedFormatError`) |
| `frontend/src/core/vault/sealedVault.ts` | Единственный путь чтения и записи запечатанного хранилища |
| `frontend/src/core/vault/sealedIndex.ts` | Поисковый индекс, только в памяти |
| `frontend/src/core/vault/conflicts.ts` | Разбор расхождений манифестов |

### 2.3. Бэкенд

* `backend/internal/sealed/**` — слепое хранилище объектов и манифестов.
* Эндпоинты под `/api/vault/sealed/*` (таблица в разделе 4).
* **В режиме `sealed` база SQLite не создаётся вообще** — plaintext-индекса не
  существует ни в каком виде.
* Эндпоинты открытой заметочной конвейерной линии (`/api/notes`,
  `/api/files`, `/api/tree`, …) в запечатанном режиме отвечают `409` с кодом
  `vault_sealed`. Второго, параллельного пути записи не существует.

## 3. Криптографическая схема и её обоснование

### 3.1. Вывод ключа из пароля: Argon2id

| Параметр | Значение | Смысл |
|---|---|---|
| Алгоритм | `argon2id` | Единственный принимаемый KDF |
| Соль | 16 случайных байт (base64) | Уникальна на хранилище, лежит в keystore |
| `m` (память) | 65536 KiB (64 MiB) | Стоимость по памяти |
| `t` (итерации) | 3 | Число проходов |
| `p` (параллелизм) | 1 | Число дорожек |
| Длина вывода | 32 байта | AES-256 |

«Лёгкий» пресет для слабых устройств: `m = 8192` (8 MiB), `t = 2`, `p = 1`.
Интерфейс прямо сообщает, что лёгкий пресет **ослабляет вывод ключа**.

Реализация — `hash-wasm` (лицензия MIT), модуль подгружается **лениво**
(`await import('hash-wasm')`), чтобы тяжёлый WASM-блок попал в отдельный чанк
бандла и не раздувал стартовый чанк приложения.

**Почему не PBKDF2.** WebCrypto умеет PBKDF2 «из коробки», но PBKDF2 — это
только функция с повторением: её стоимость линейна по числу итераций и почти не
зависит от памяти. Обычные GPU/ASIC перебирают миллионы итераций в секунду.
Argon2id — memory-hard: стоимость складывается из реально занятой памяти, что
делает аппаратный перебор экономически бессмысленным. Для модели угроз
«украденное хранилище + офлайн-перебор» это правильный ответ.

**Почему не «просто придумать пароль посложнее».** Длина пароля помогает, но не
измеряет работу: Argon2id добавляет фиксированную дорогую работу поверх
любого пароля, поэтому слабый пароль «дорожает» в одинаковой мере для всех
пользователей.

### 3.2. Шифрование данных: AES-256-GCM

* Алгоритм: `AES-GCM`, ключ 256 бит, `crypto.subtle`.
* **Новый 96-битный nonce на каждый объект** из CSPRNG (`crypto.getRandomValues`).
  Повтор nonce под одним ключом — фатален для GCM, поэтому nonce генерируется
  заново при каждой записи и никогда не выводится из содержимого.
* **Заголовок контейнера — AAD (associated data).** Заголовок зашифрован «не
  явно», но аутентифицирован: изменённый заголовок (например, подменённый
  `epoch`) ломает проверку GCM, и контейнер не расшифровывается.
* Изменённый шифротекст или неверный ключ ломают тег GCM (16 байт) и дают
  `AuthenticationError`.

### 3.3. Иерархия ключей

```
   мастер-пароль
        │
        │  Argon2id (m=64 MiB, t=3, p=1) + соль
        ▼
      KEK  (key encryption key, AES-256, неэкспортируемая)
        │
        │  AES-GCM, AAD = id эпохи (4 байта, big endian)
        ▼
      DEK  (data encryption key, 32 случайных байта)
        │
        │  AES-256-GCM, AAD = заголовок контейнера
        ▼
   объекты и манифесты
```

Свойства схемы:

* **Пароль нигде не хранится.**
* **DEK нигде не хранится в открытом виде** — только завёрнутая (wrapped) копия
  в keystore.
* **Ключи живут только в памяти вкладки.** KEK импортируется как
  неэкспортируемый ключ (`extractable: false`), DEK живёт как `CryptoKey`.
* **Ключ восстановления** — случайные 32 байта, которые пользователь сохраняет
  себе; он заворачивает тот же DEK с AAD `noto-recovery-v1`. Это явный,
  криптографически обоснованный механизм восстановления; «тайного» восстановления
  на стороне разработчика нет.

### 3.4. Эпохи ключей

Keystore — это список эпох. У каждой эпохи свой `id` и своя завёрнутая копия DEK.

* **Смена пароля пере-оборачивает DEK и НЕ перешифровывает объекты.** Это
  главное свойство: смена пароля стоит секунд, а не часов, и не трогает
  содержимое.
* Новая эпоха **добавляется** в список, старые остаются. Старый пароль
  продолжает открывать старые эпохи, старый клиент по-прежнему может открыть
  хранилище. При разблокировке эпохи перебираются от новых к старым.
* Формат **готовит** ротацию самого DEK (новая эпоха с новым DEK), но
  перешифровка объектов при ротации выполняется **лениво, в работе** — на
  текущий момент в формате есть только эпоха с завёрнутым DEK.

## 4. API бэкенда в режиме `sealed`

| Метод и путь | Назначение |
|---|---|
| `GET /api/vault/sealed/status` | Режим хранилища, версия формата, число объектов, список поколений манифеста |
| `GET /api/vault/sealed/keystore` | Открытый keystore (параметры KDF, эпохи, необязательный блок восстановления) |
| `PUT /api/vault/sealed/keystore` | Записать keystore |
| `GET /api/vault/sealed/objects` | Список идентификаторов объектов |
| `GET /api/vault/sealed/objects/{id}` | Отдать байты объекта |
| `PUT /api/vault/sealed/objects/{id}` | Записать байты объекта |
| `DELETE /api/vault/sealed/objects/{id}` | Удалить объект |
| `GET /api/vault/sealed/manifests` | Список поколений манифеста |
| `GET /api/vault/sealed/manifests/{gen}` | Отдать запечатанный манифест |
| `PUT /api/vault/sealed/manifests/{gen}` | Записать запечатанный манифест |
| `DELETE /api/vault/sealed/manifests/{gen}` | Удалить манифест |
| `POST /api/vault/sealed/enable` | Переключить сервер в режим `sealed` |

Ограничения бэкенда: максимальный размер объекта — 64 MiB, максимальный размер
keystore — 1 MiB, идентификатор — ровно 32 строчных hex-символа, поколение
манифеста — положительное целое. Нарушение этих правил даёт `400` с кодами
`invalid_id` / `invalid_generation` / `payload_too_large`.

Ограничения бэкенда — это защита от испорченного клиента, а не защита от
злоумышленника: бэкенд не может проверить криптографическую целостность
контейнера, он лишь возвращает байты клиенту.

## 5. Формат (версия 1)

### 5.1. Раскладка хранилища

```
<vault>/
└── .noto/
    ├── config.json            {"mode":"sealed","format":1}
    ├── keystore.json          открытый keystore: параметры KDF, эпохи, recovery
    ├── objects/
    │   └── <xx>/<id>.nse      запечатанные объекты (256 шартов по первым двум hex)
    └── manifests/
        └── <gen>.nse          запечатанные манифесты
```

`config.json` не содержит секретов: режим и версия формата публичны.
`keystore.json` тоже не содержит ключа — только завёрнутые копии DEK.

### 5.2. Контейнер объекта

```
  смещение  размер  поле
  ────────────────────────────────────────────
  0         8       magic "NOTOSEAL"
  8         2       version   (u16, big endian)
  10        2       flags     (u16, big endian, сейчас всегда 0)
  12        4       epoch     (u32, big endian)
  16        12      nonce     (96 бит, IV для GCM)
  28        …       ciphertext
  …         16      GCM tag
```

* Итого заголовок — **28 байт**, и именно эти 28 байт идут в AAD.
* Версия, которую клиент не знает, отвергается с понятной ошибкой
  (`Unsupported sealed format version`), а не «пытается расшифровать».
* Магическое число позволяет бэкенду отличить контейнер от мусора, не зная
  ничего о криптографии.

### 5.3. Идентификаторы объектов

Идентификатор — **32 строчных hex-символа** (16 случайных байт) и **никогда не
зависит от содержимого**. Это осознанное требование: если бы идентификатор
вычислялся из содержимого (например, как hash), провайдер смог бы сравнить
объекты и определить, что две заметки одинаковы. Случайный идентификатор этого
не позволяет.

### 5.4. Манифест

Манифест запечатан наравне с остальным — это единственное место, где лежит
дерево, и его содержимое тоже не видно провайдеру.

Манифест хранит:

* формат и **монотонное поколение** (`generation`);
* время создания и эпоху ключа, которой зашифрованы объекты поколения;
* дерево: тип узла (`file` / `folder`), имя, путь, путь родителя, идентификатор
  объекта с содержимым (`contentId`), размер, время изменения, ревизию, времена
  создания и обновления, счётчик заметок и счётчик подпапок;
* записи корзины (удалённые узлы с исходным путём и временем удаления);
* необязательный список расхождений при слиянии (`conflicts`) — он никогда не
  сливается молча.

**Порядок записи: сначала объекты, потом манифест.** Авария может оставить
«осиротевший» объект, но не может оставить манифест, ссылающийся на
отсутствующий объект.

**Хранятся последние 5 поколений манифеста** (`MANIFEST_GENERATIONS_KEPT = 5`),
остальные удаляются — это компромисс между историей и размером.

### 5.5. Большие вложения

Вложения больше 4 MiB запечатываются **чанками по 4 MiB**
(`ATTACHMENT_CHUNK_BYTES = 4 * 1024 * 1024`). **Индекс чанка входит в AAD**,
поэтому чанки нельзя переставить местами и нельзя заменить чанком другого
файла: проверка GCM не сойдётся.

### 5.6. Поисковый индекс

Индекс поиска строится **в браузере из расшифрованного содержимого** и живёт
только в памяти вкладки. На диск он никогда не пишется и в открытом виде не
существует ни в одном файле. Обратная сторона: после блокировки хранилища
индекс исчезает, и поиск заработает снова только после разблокировки.

## 6. Жизненный цикл ключей

### 6.1. Создание хранилища (мастер)

Мастер предлагает выбор: **создать новое запечатанное хранилище** или
**перевести существующее открытое** (раздел 8). Далее:

1. ввод мастер-пароля и его подтверждения;
2. индикатор стойкости пароля;
3. предупреждение, что **без пароля и без ключа восстановления ничего не
   восстановить**;
4. генерация ключа восстановления;
5. экран успеха.

> **Статус:** интерфейс мастера — **готово** (rontend/src/components/VaultSetupDialog.tsx).

### 6.2. Разблокировка

Отдельный экран: имя хранилища, поле пароля с переключателем видимости, кнопка
**«Разблокировать»**, отправка по клавише Enter, автофокус на поле. Ошибка
единая и не выдаёт деталей — «неверный пароль или повреждённое хранилище»:
иначе ошибка стала бы оракулом для подбора.

> **Статус:** экран разблокировки — **готово** (rontend/src/components/VaultUnlockScreen.tsx).

### 6.3. Блокировка

Блокировка происходит:

* по требованию пользователя;
* по простою (таймаут — настройка, по умолчанию 15 минут);
* при потере окном фокуса.

При блокировке материал ключей уничтожается, манифест и поисковый индекс
очищаются, редактор опустошается, локальные черновики удаляются.

> **Статус:** экран блокировки и таймаут простоя — **готово** (rontend/src/components/VaultSecuritySection.tsx, rontend/src/core/vault/autoLock.ts).

### 6.4. Смена пароля

Пере-обёртывается только DEK. Объекты не трогаются, поэтому смена пароля
занимает секунды и не зависит от объёма хранилища.

### 6.5. Проверка целостности

Каждый объект читается и расшифровывается заново. Повреждённый объект
сообщается **по своему идентификатору**, а не по названию заметки: в
запечатанном режиме название не должно утекать туда, где его не знают.

> **Статус:** пользовательская проверка целостности — **готово** (раздел «Безопасность хранилища» в настройках).

## 7. Правила для разработчиков плагинов

* Плагин использует **тот же API, что и раньше**, и никогда не видит мастер-пароль,
  KEK или DEK.
* Материал ключей живёт в `src/core/crypto/keys` и `src/core/crypto/sealed`, а
  **проверка границ** (`frontend/scripts/check-boundaries.mjs`, правила **R11** и
  **R12**) запрещает любой импорт этих модулей за пределами
  `src/core/crypto/**` и `src/core/vault/**`. Нарушение — падение
  `npm run check:boundaries`, а не замечание на ревью.
* Плагину, которому нужно знать состояние хранилища, доступна новая
  необязательная возможность **`ctx.vault`**: `mode`, `locked`, версия формата,
  `isEncrypted`. Версия API плагинов поднимается с `1.0.0` до `1.1.0`; изменение
  **аддитивное**, существующие плагины с `minApiVersion: "1.0.0"` продолжают
  работать без изменений.
* Плагин **не должен** читать файлы хранилища напрямую (никаких `fetch` по
  путям в `.noto`) и **не должен** кэшировать содержимое заметки за пределами
  ядра: расшифрованный текст не имеет права покидать память ядра.

> **Статус:** `ctx.vault` и версия API плагинов `1.1.0` — **готово**
> (`PLUGIN_API_VERSION = '1.1.0'` в `frontend/src/plugins/contract.ts`); правила
> `R11` и `R12` проверяющего скрипта не дают плагину дотянуться до ключевого
> материала.

## 8. Миграция с открытого хранилища

Миграция — единственный момент, когда открытые данные должны исчезнуть с диска,
поэтому она сделана максимально консервативно.

| Шаг | Что происходит |
|---|---|
| Журнал | `.noto/migration.json` позволяет продолжить миграцию после аварии |
| Staging | Миграция пишет в промежуточную область; исходное хранилище никогда не переводится наполовину |
| Проверка | Каждый перенесённый объект расшифровывается заново и сравнивается |
| Переключение | Переключение режима атомарно |
| Удаление | Открытые оригиналы удаляются **только** после проверки и **только** после явного подтверждения пользователя |

Приложение честно говорит, что **не может стереть копии**, которые остались в
истории версий облачного провайдера, в его снимках и в резервных копиях. Если
это важно, очистите историю версий в настройках провайдера вручную.

> **Статус:** миграция, журнал и переключение режима — **готово**
> (`frontend/src/core/vault/migration.ts`, `frontend/src/components/VaultMigrationDialog.tsx`);
> удаление открытых оригиналов выполняет сервер по явному запросу
> `POST /api/vault/sealed/purge-plaintext` — и только после подтверждения.
>
> Сервер удаляет не только файлы заметок: он освобождает и заменяет на
> «заблокированный» конвейер открытых заметок (база SQLite), затем удаляет
> саму базу (`noto.db`, `noto.db-wal`, `noto.db-shm`) и корзину хранилища.
> Иначе plaintext остался бы в базе — она тоже хранит текст заметок.

## 9. Совместимость с облачными файловыми сервисами

Noto **не имеет собственной службы синхронизации**. Совместимость достигается
дизайном формата, а не протоколом.

* **Объекты неизменяемы.** Новое содержимое — это новый объект с новым
  идентификатором. Старая версия никогда не перезаписывает новую: синхронизатор
  не может «принести» старый файл поверх свежего.
* **Манифест пишется как новое поколение.** Если синхронизатор создал два файла
  с разными поколениями, клиент **открывает оба**, показывает конфликт и
  **никогда молча не перезаписывает более новую версию**. Расхождения по
  содержимому перечисляются пользователю, а не сливаются автоматически.
* **Повреждённый или недокачанный объект** не проходит проверку GCM и
  сообщается как ошибка **этого** объекта; остальные объекты остаются
  пригодными.
* **Синхронизация — не резервное копирование.** Приложение говорит об этом
  прямо: провайдер может не хранить историю, может удалить файл по политике
  хранения, может «схлопнуть» папку. Настоящий бэкап — отдельная задача
  пользователя.

## 10. Как проверить безопасность

### 10.1. Юнит-тесты крипто-ядра

```powershell
cd frontend
npx vitest run src/core/crypto
```

Покрываются: параметры KDF и соль, кодирование/разбор заголовка контейнера,
seal/open, отказ при подменённом шифротексте, отказ при подменённом заголовке,
создание и разблокировка keystore, пере-обёртывание при смене пароля,
ключ восстановления.

### 10.2. Юнит-тесты слоя хранилища

```powershell
cd frontend
npx vitest run src/core/vault
```

### 10.3. Тесты бэкенда

```powershell
cd backend
go test ./internal/sealed/... ./internal/api/...
```

### 10.4. Интеграционный тест «настоящих файлов на диске»

Это главная проверка заявления «на диске лежит только шифротекст».

Тест:

1. создаёт заметку с **уникальным маркером** (например, `noto-plaintext-marker-9f2c…`);
2. **перебирает весь каталог хранилища** и ищет маркер в:
   * объектах (`objects/**`),
   * манифестах (`manifests/**`),
   * файле базы SQLite и его `-wal` / `-shm`,
   * временных файлах и файлах конфигурации;
3. ожидает **ноль вхождений**.

Как запустить — так же, как остальные тесты фронтенда:

```powershell
cd frontend
npx vitest run src/core/vault
```

Как читать провал:

| Симптом | Что это значит |
|---|---|
| Маркер найден в `objects/**` | Утечка в крипто-ядре: объект записан без шифрования или AAD/шифрование не применены |
| Маркер найден в `manifests/**` | Манифест записан в открытом виде (или расшифрован и сохранён) |
| Маркер найден в `noto.db`, `noto.db-wal`, `noto.db-shm` | В режиме `sealed` база вообще не должна создаваться — это дефект режима |
| Маркер найден во временном файле | Промежуточный plaintext попал на диск: нарушен порядок «сначала шифрование, потом запись» |
| Маркер найден в `keystore.json` | В keystore попал plaintext — нарушен контракт keystore |

> **Статус:** интеграционный тест, сканирующий **реальные** файлы на диске, —
> **написан и проходит** (`e2e/specs/encryption.spec.ts`, `e2e/helpers/vault-scan.ts`).
> Сценарий создаёт настоящее хранилище во временном каталоге, пишет в него
> две заметки с уникальными маркерами, переводит хранилище в запечатанный
> режим через интерфейс и затем проверяет, что **ни один** байт **ни одного**
> файла хранилища не содержит этих маркеров. Пять проверок сценария: миграция
> проходит, на диске лежит только шифротекст, после перезагрузки хранилище
> заперто, правильный пароль открывает заметки снова, а сервер разрешает
> WebAssembly вывода ключа (`wasm-unsafe-eval` в `script-src`).

### 10.5. Полная проверка

```powershell
.\scripts\verify.ps1 -E2E -Bench
```

## 11. Формат: что уже есть и что дальше

### Версия 1 (текущая)

* Контейнер `NOTOSEAL`, версия 1, AAD = 28 байт заголовка.
* Argon2id + AES-256-GCM, keystore с эпохами и ключом восстановления.
* Манифест с монотонным поколением, хранение 5 поколений.
* Случайные идентификаторы объектов, чанки по 4 MiB с индексом в AAD.

### Версия 2 (в плане)

| Изменение | Зачем |
|---|---|
| XChaCha20-Poly1305 как альтернатива AES-GCM | Больший безопасный nonce (192 бита) — снимает вопрос повтора nonce при потоковой записи и при переносе формата на другие реализации |
| Постквантовый KDF | Защита от будущего квантового противника, способного ослабить аргумент «перебор Argon2id дорог» |
| Перешифровка объектов при ротации DEK | Формат уже позволяет новую эпоху с новым DEK; не хватает только самого перешифровывания (ленивого) |
| Явное согласование формата между устройствами | Устройства разных версий должны явно договариваться о формате, а не падать при разнице версий |

## 12. Сводка: гарантии и ограничения

| Гарантия | Ограничение |
|---|---|
| Провайдер и сервер не могут прочитать содержимое | Они видят метаданные: размеры, время, идентификаторы |
| Подмена данных обнаруживается (AES-GCM) | Обнаружение не восстановление: нужен бэкап |
| Ключи не покидают браузер | Клиент может быть модифицирован; ключ можно украсть из разблокированной сессии |
| Пароль не хранится | Без пароля и без ключа восстановления хранилище не открыть |
| Смена пароля не перешифровывает объекты | Старый пароль продолжает работать для старых эпох — это осознанный компромисс |
| Нет plaintext-базы в режиме `sealed` | В открытом режиме база существует, как и раньше |
| Удалённые объекты не восстанавливаются из истории провайдера | Копии в истории версий, снимках и бэкапах провайдера остаются |
| Поиск работает без сервера | Индекс существует только в памяти вкладки и исчезает при блокировке |
