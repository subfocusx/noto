# Хранилище заметок (vault)

Документ описывает, где Noto хранит заметки, как пользователь выбирает папку
и как работает переключение хранилища на лету.

Идея взята из Obsidian: заметки лежат обычными Markdown-файлами в папке,
которую выбрал пользователь, а служебные данные приложения спрятаны рядом в
скрытой подпапке `.noto`. Папку с заметками можно открыть любым другим
редактором Markdown.

---

## 1. Раскладка хранилища

```
<vault>/
├── note.md              заметки лежат прямо в папке хранилища
├── journal/
│   └── 2026-01-01.md
└── .noto/               внутренние данные Noto (скрытая папка)
    ├── noto.db          база SQLite (user_version = 1)
    ├── trash/           удалённые заметки
    └── attachments/     вложения
```

- `.noto` никогда не попадает в дерево заметок: обход файлов пропускает любой
  сегмент пути, который начинается с точки (`backend/internal/notes/service.go`).
- Конфигурация хранилища лежит **вне** хранилища — в пользовательской папке
  конфигурации (`os.UserConfigDir()/noto/vault.json`), чтобы смена папки её не
  уничтожила. Переопределяется переменной окружения `NOTO_VAULT_FILE`.

---

## 2. Переменные окружения

| Переменная | Смысл |
|---|---|
| `NOTO_DATA_DIR` | каталог служебных данных (БД, корзина, вложения) **по умолчанию** |
| `NOTO_NOTES_DIR` | каталог заметок **по умолчанию** |
| `NOTO_VAULT_FILE` | путь к файлу конфигурации хранилища |
| `NOTO_VAULT_FIXED` | хранилище зафиксировано: сменить папку на лету нельзя |

`NOTO_DATA_DIR` и `NOTO_NOTES_DIR` имеют приоритет над `vault.json`: такой
запуск использует обычную раскладку, а не раскладку хранилища. Они **только
задают расположение по умолчанию** и не запрещают сменить папку на лету.

Запрет смены задаёт **только** `NOTO_VAULT_FIXED=1` (любое значение, кроме
пустой строки, `0` и `false`). Тогда сервер отвечает `400` с кодом
`vault_fixed`, а приложение показывает зафиксированное хранилище как штатное
состояние: кнопка смены остаётся на месте, но помечена `aria-disabled`, и
никакого баннера-ошибки не появляется. Именно этим флагом пользуются
end-to-end тесты (`playwright.config.ts`).

## 3. API

### `GET /api/vault`

```json
{ "configured": true, "path": "D:\\Notes", "notesDir": "D:\\Notes", "fixed": false }
```

- `configured` — выбрана ли папка хранилища;
- `path` — абсолютный путь папки хранилища (пусто, если используется раскладка
  по умолчанию и хранилище не зафиксировано окружением);
- `notesDir` — каталог с заметками;
- `fixed` — можно ли сменить хранилище на лету.

### `POST /api/vault`

Тело: `{ "path": "D:\\Notes" }`. Путь проверяется: он должен существовать, быть
каталогом и быть доступным на запись. При успехе конфигурация сохраняется,
сервис переключается на новую папку, дерево заметок перечитывается.

Ответ: `{ "ok": true, "path": "D:\\Notes" }`.

Ошибки: `400 bad_request` (путь не передан), `400 invalid_path` (путь не
пригоден), `404 not_found` (каталога нет), `500 internal` (не удалось открыть
хранилище; сохранённая конфигурация восстанавливается).

### `DELETE /api/vault`

Сбрасывает конфигурацию и возвращает сервис к раскладке по умолчанию.

### `GET /api/vault/browse?path=<путь>`

Список подкаталогов для диалога выбора папки:

```json
{
  "path": "D:\\",
  "parent": "",
  "dirs": [{ "name": "Notes", "path": "D:\\Notes" }]
}
```

Эндпоинт только читает: возвращает имена подкаталогов, без файлов и без
скрытых каталогов (`.`‑префикс). Пустой `path` означает корень тома.

## 4. Переключение на лету

`api.Server` хранит сервис заметок под `sync.RWMutex` (`service()` /
`setService()`). При смене хранилища старый сервис освобождается не сразу, а
через 5 секунд (`closeGrace`), чтобы запросы, которые уже выполняются, успели
завершиться.

Фронтенд после успешного `POST /api/vault` заново читает дерево заметок, так
что в дереве сразу видны файлы новой папки.

## 5. Интерфейс

- При первом старте, когда хранилище не выбрано, открывается диалог
  **«Choose the storage of the notes»** (`frontend/src/components/VaultPicker.tsx`).
  Он показывает текущий каталог, родительский каталог и подкаталоги; скрытые
  каталоги не показываются.
- Диалог можно пропустить: приложение продолжит работать с раскладкой по
  умолчанию и покажет баннер.
- Сменить хранилище позже можно через путь в шапке левой колонки (клик по
  пути) или через иконку рядом с ним — открывается **быстрое меню**
  (`frontend/src/components/VaultSwitchMenu.tsx`): текущее хранилище, список
  недавних и пункт «Choose another folder…», который открывает диалог выше.
  То же меню открывается из палитры команд (`app:switch-vault`).
- Список недавних хранилищ живёт в настройках пользователя
  (`prefs.vaultRecents`, не больше 8 записей): сервер держит одно хранилище,
  поэтому история хранилищ — это забота клиента.
- После смены хранилища клиент заново читает режим нового хранилища и сбрасывает
  ключевой материал прежнего (`lockVault`). Хранилище, которое зашифровано,
  показывает экран пароля, а не заметки прошлого хранилища.
- Хранилище, зафиксированное окружением (`NOTO_VAULT_FIXED`), менять нельзя:
  кнопка остаётся на месте, но помечена `aria-disabled` и ничего не открывает.
- Клиент API: `frontend/src/api/vault.ts` (`getVault`, `setVault`, `browseVault`).

## 7. Два режима хранилища

Хранилище заметок бывает двух видов, и режим — это факт на диске, а не
состояние процесса:

| | Открытое хранилище | Запечатанное хранилище |
|---|---|---|
| Что лежит на диске | обычные `.md` | только шифротекст в `.noto/` |
| Кто шифрует | никто | браузер (`frontend/src/core/crypto/**`) |
| Что знает сервер | содержимое заметок | ничего: он хранит байты по идентификатору |
| Где живёт ключ | — | только в памяти вкладки, в виде неэкспортируемого `CryptoKey` |
| Поиск | индекс FTS5 в SQLite | индекс строится в браузере из расшифрованного текста, живёт только в памяти вкладки |
| Что отвечает сервер | обычные ответы API | `409 vault_sealed` на всех «открытых» маршрутах |

Режим определяется файлом `<vault>/.noto/config.json`:

```json
{ "mode": "sealed", "format": 1 }
```

`mode` и `format` публичны: секрета в файле нет.

### 7.1. Правило одного пути

Приложение **никогда** не работает с двумя режимами одновременно. Стор
(`frontend/src/core/store/**`) всегда обращается к `VaultService`
(`frontend/src/core/vault/vaultService.ts`) — единственной точке входа:

* в открытом режиме установлен адаптер над API заметок
  (`createOpenVaultService()`);
* в запечатанном режиме — адаптер над запечатанным хранилищем
  (`createSealedVaultService()`).

Адаптер меняется по подписке на сессию хранилища
(`syncVaultServiceWithSession()`). Стор, интерфейс и плагины работают с
одним и тем же интерфейсом в обоих режимах, поэтому переход в
запечатанный режим не меняет их ни на строчку.

Второй рубеж — сервер. Как только хранилище запечатано, все маршруты
открытого конвейера отвечают `409` с кодом `vault_sealed`
(`backend/internal/api/api.go`, обёртка `openRoute`). Ответ сервера —
`the vault is sealed: the notes are encrypted by the client and the server
stores only ciphertext`.

Формат, параметры криптографии и границы гарантий описаны в
[`ENCRYPTION.md`](ENCRYPTION.md); маршруты — в [`API.md`](API.md).

## 8. Раскладка запечатанного хранилища

```
<vault>/
└── .noto/
    ├── config.json          {"mode":"sealed","format":1}
    ├── keystore.json        параметры KDF, эпохи с завёрнутыми DEK, блок восстановления
    ├── objects/
    │   └── <xx>/<id>.nse    запечатанные объекты (256 шартов по первым двум hex)
    └── manifests/
        └── <gen>.nse        запечатанные манифесты
```

* `config.json` — режим и версия формата. Секретов не содержит.* `keystore.json` — **открытый** keystore: параметры KDF, соль, список эпох с
  завёрнутыми копиями ключа данных и необязательный блок восстановления.
  Ключа в открытом виде там нет: только завёрнутые копии.
* `objects/<xx>/<id>.nse` — содержимое заметок и вложений. Идентификатор —
  32 строчных hex-символа (16 случайных байт) и **не зависит** от
  содержимого: иначе провайдер смог бы сравнить объекты.
* `manifests/<gen>.nse` — дерево хранилища. Имена заметок лежат здесь и тоже
  запечатаны: это единственное место, где они живут.

В открытом режиме `.noto` — служебный каталог приложения: там лежат база
(`noto.db`), корзина и вложения (`backend/internal/vault/vault.go`). В
запечатанном режиме на диске остаётся только перечисленное выше: открытых
заметок нет вообще.

Правила формата (заголовок контейнера, AAD, порядок «сначала объекты, потом
манифест», число хранимых поколений) — в [`ENCRYPTION.md`](ENCRYPTION.md),
разделы 5.1–5.4.

### 8.1. Что пишет сервер, а что — клиент

| Кто | Что | Куда |
|---|---|---|
| Сервер (`backend/internal/sealed`) | байты объектов | `.noto/objects/<xx>/<id>.nse` |
| Сервер | байты манифестов | `.noto/manifests/<gen>.nse` |
| Сервер | keystore (как есть, без изменений) | `.noto/keystore.json` |
| Сервер | режим и версия формата | `.noto/config.json` |
| Клиент | сам ключ, шифрование, расшифровка, поисковый индекс | нигде на диске |

Сервер **не разбирает** контейнер и **не знает** ключа: он оперирует байтами.
Всё, что он делает с запечатанными данными, — сохранить, отдать и удалить.

## 9. Миграция открытого хранилища

Миграция — единственный момент, когда открытые данные должны исчезнуть с
диска, поэтому порядок шагов и есть её безопасность
(`frontend/src/core/vault/migration.ts`):

1. **read** — читаются все заметки открытого хранилища; ещё ничего не
   записано;
2. **encrypt** — каждая заметка запечатывается и кладётся объектом, манифест
   пишется **новым поколением после** объектов;
3. **verify** — каждый запечатанный объект читается заново, расшифровывается и
   сравнивается с источником; расхождения собираются, и до их устранения
   переключение режима **не происходит**;
4. **switch** — сервер переключается в запечатанный режим (`409 vault_sealed`
   с этого момента);
5. **purge** — открытые оригиналы удаляются **отдельным** явным вызовом
   `POST /api/vault/sealed/purge-plaintext`, который интерфейс делает только
   после подтверждения пользователя.

Открытый текст переживает любой сбой: он удаляется тогда и только тогда, когда
пользователь сам попросил.

### 9.1. Журнал миграции

Журнал лежит **внутри запечатанного манифеста** (`manifest.migration`), а не
отдельным файлом: падение не теряет его. Журнал хранит фазу
(`reading` / `encrypting` / `verifying` / `switching` / `done`), список уже
перенесённых путей, список перенесённых вложений, список неудачных путей и
вложений и время последнего обновления. После аварии миграция продолжается с
недостающих заметок, а не начинается заново.

### 9.2. Что приложение честно говорит пользователю

Приложение прямо предупреждает, что **не может стереть копии**, которые
остались:

* в истории версий облачного провайдера (OneDrive, Google Drive, Яндекс.Диск);
* в его снимках состояния;
* в резервных копиях, которые провайдер делает сам.

Если это важно, историю версий нужно очистить в настройках провайдера
вручную — Noto до неё не имеет доступа.

Там же сказано второе, менее очевидное: **синхронизация — не резервное
копирование**. Провайдер может не хранить историю, может удалить файл по
политике хранения, может «схлопнуть» папку. Настоящий бэкап — отдельная
задача пользователя.

## 11. Что может и что не может плагин

Плагин работает с запечатанным хранилищем **тем же** API, что и всегда:
`ctx.api.getNote`, `ctx.api.saveNote`, `ctx.api.getTree`, `ctx.api.search`.
Разницы для плагина нет — плагин не знает, запечатано хранилище или нет.

Плагин **не может**:

* получить мастер-пароль, KEK или DEK — это запрещено правилами R11 и R12
  проверки границ (`frontend/scripts/check-boundaries.mjs`);
* читать файлы `.noto` напрямую (`fetch` по путям хранилища);
* кэшировать содержимое заметки за пределами ядра.

Плагин **может** узнать состояние хранилища через необязательное
`ctx.vault` (`mode`, `encrypted`, `locked`, `formatVersion`) — см.
[`PLUGIN_API.md`](PLUGIN_API.md), раздел 4.
