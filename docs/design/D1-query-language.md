# D1 — Язык запросов

**Status:** Implemented

**Связанные документы:** `docs/QUERY_LANGUAGE.md` (источник истины по
синтаксису и семантике), `shared/query-vectors.json` (golden-векторы),
`docs/CONTRACT.md` (эндпоинты запроса).

---

## Context

Noto умеет искать по тексту (FTS5) и показывать дерево по папкам. Этого
не хватало: пользователю нужен способ спросить «что у меня есть по тегу
`work` за последнюю неделю, без задач и с картинками» — и получить тот же
ответ в двух режимах хранения.

Проблема в том, что режимов два:

* **открытый режим** — данные лежат на диске, база SQLite, запрос можно
  превратить в SQL;
* **запечатанный режим** — сервер не видит данных, запрос исполняется в
  браузере по дереву в памяти.

Значит, язык запросов должен быть один, а исполняться — в двух местах. Если
у каждого режима будет свой синтаксис, через полгода они разойдутся, и
пользователь получит два разных ответа на один и тот же вопрос.

Дополнительные требования:

* язык должен быть **безопасным по умолчанию** — никакого исполнения
  произвольного кода запроса;
* он должен **жить в двух языках** (Go и TypeScript) без расхождения;
* его должно быть **легко описать** — иначе его не осилят ни пользователи, ни
  документация;
* новые зависимости в этом репозитории нежелательны (см. `AGENTS.md` §5).

## Decision

1. **Свой мини-язык по мотивами фильтров `usememos/memos` (MIT).** Синтаксис
   полей и операторов (`==`, `!=`, `>`, `in`, `contains`, `startsWith`,
   `endsWith`), логические связки `&&` / `||` / `!`, скобки, значения
   (`'строки'`, числа, `true`/`false`, `now`, `today`, относительные
   интервалы `now - 7d`) и списки `[a, b]`.

2. **Без `cel-go` и без любого рантайма выражений.** Грамматика фиксирована и
   разбирается собственным парсером; запрос не может быть исполнен как
   программа.

3. **Промежуточное представление (IR) — единственный контракт между двумя
   исполнениями.** Разбор даёт IR:
   `and{l,r} | or{l,r} | not{e} | cmp{f,op,v} | truthy{f}` и значения
   `str | num | bool | list | now | today | rel{base,off}`.
   IR не знает ни про SQL, ни про JavaScript.

4. **Два компилятора от одного IR.**
   * Go: IR → SQL с параметрами (`backend/internal/query`) — значения всегда
     идут параметрами, инъекция SQL невозможна;
   * TypeScript: IR → предикат по дереву в памяти
     (`frontend/src/core/query`) — исполняется в запечатанном режиме.

5. **Golden-векторы как контракт.** `shared/query-vectors.json` — это файл
   с примерами: текст запроса → ожидаемый IR (и, где уместно, ожидаемый
   результат). Оба исполнения читают **один и тот же файл** и обязаны дать
   байт-в-байт одинаковый IR. Тест конформанса в Go и в TypeScript падает
   при любом расхождении: язык не может разъехаться незаметно.

6. **Ошибки — часть контракта.** Сообщения об ошибках стабильны
   (`unknown field: <name>`, `unknown operator: <name>`,
   `operator <op> does not fit the field <field>`), пустой запрос не ошибка, а
   «ничего не подошло».

7. **Регулярных выражений нет.** Синтаксис регулярных выражений различается
   между движками, и язык стал бы непредсказуемым.

## Consequences

**Возможности:**

* один и тот же вопрос работает в обоих режимах хранения — проверено
  golden-векторами, а не обещанием;
* язык маленький: его целиком помещается в одну страницу документации, его
  можно выучить за десять минут;
* запросы безопасны: нет ни рантайма, ни строки в SQL, ни `eval`;
* golden-векторы дают регрессионную сетку: любое изменение грамматики
  видно сразу.

**Издержки и обязанности:**

* язык не выражает всё: агрегаций, соединений, подзапросов, вычисляемых
  полей пользователя нет — и не будет без нового решения;
* поддерживать IR, два компилятора и набор golden-векторов — это постоянная
  работа: изменение грамматики обязано идти вместе с векторами и с обоими
  компиляторами;
* фронтенд тащит свою копию разбора — дублирование кода, сдержанное
  golden-векторами.

**Что из этого следует для других карточек:**

* D2 (производные свойства) обязана опираться на тот же IR и на те же
  векторы: поле, которое появляется в IR, появляется и в golden-векторах;
* D4 (сохранённые представления) хранит текст запроса, поэтому текст запроса
  — это **долгоживущий формат**: его нельзя менять без версии.

## Alternatives considered

| Вариант | Почему отвергнут |
|---|---|
| `cel-go` (Google Common Expression Language) | Мощный и проверенный, но это новая зависимость, тяжёлая ради одного поля, с собственной семантикой типов и своим фронтенд-портом (в Go и в браузере пришлось бы тащить две разные реализации). Наш набор полей мал — весь язык помещается в 200 строк. |
| SQL, написанный пользователем | В открытом режиме выглядит естественно, но в запечатанном режиме его выполнить нечем, а наивная склейка строки — это инъекция. Плюс интерфейс с SQL — это интерфейс с SQL. |
| Фильтры как структура объекта (`{tag: ['work'], updatedAfter: ...}`) | Проще разбирать, но невозможно набрать руками и невозможно показать в поле ввода как «вопрос пользователя». Кроме того, структура объекта плохо переживает эволюцию полей. |
| Один компилятор — только SQL | В запечатанном режиме сервер не видит данных, исполнять нечего. |
| Один компилятор — только предикат в браузере | Потеряем индекс: на большой библиотеке фильтрация «в лоб» по всем заметкам недопустима. |
| Два независимых языка (по одному на режим) | Ровно та расхождение, ради которой карточка и написана: пользователь не должен помнить, открыт он или запечатан. |
| Перевести запрос в AST на этапе фронтенда и передавать AST на сервер | AST стал бы частью публичного API и вторым контрактом; при изменении формата старый клиент и новый сервер расходятся. Текст запроса + golden-векторы — контракт, который читается глазами. |

## Amendments

2026-10-25 — язык получил оператор регулярных выражений: `matches` и
префикс `match:` (`backend/internal/query/regex.go`,
`frontend/src/core/query/regex.ts`). Бэкенд компилирует выражение через RE2,
браузер — через `RegExp` JavaScript, поэтому у выражений есть свои
golden-векторы `shared/vectors/regex.json`; ограничение (движки не
эквивалентны) записано в `docs/NOT_IMPLEMENTED.md`, пункт B1.
